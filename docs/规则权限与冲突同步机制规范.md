# 规则所有权与冲突同步机制规范 (Conflict & Ownership Specification)

## 1. 业务背景与设计准则

在 O-Maid 云端共享与多人协作体系中，存在两类典型角色与数据流转行为：
1. **原作者 (Author)**：创建规则并首次公开发布至云端的创作者。
2. **下载者/使用者 (Consumer)**：从云端大厅浏览、发现并下载规则至本地使用的用户。

### 核心设计原则
1. **原作者主权不可侵犯 (Strict Ownership Protection)**：
   - 用户 A 发布的规则，属于用户 A。
   - 用户 B 下载后，即使在本地进行了二次编辑或定制修改，**坚决不允许直接覆盖/同步回用户 A 的云端原版规则**。
2. **本地劳动成果保护 (Local Modification Immunity)**：
   - 用户 B 在本地对规则所做的修改属于其个人工作成果；
   - 当用户 B 触发「🔄 刷新」同步时，系统**严禁静默暴力覆写**已改动的本地规则。
3. **透明可控的冲突仲裁 (Explicit Conflict Resolution)**：
   - 刷新时若检测到“本地已修改”且“云端有更新”，必须在界面上将冲突词条**显著标注出来**，并提供直观的选择确认框，由用户决定是「覆盖」还是「保留」。

## 2. 所有权与写权限鉴权规范 (Ownership & Write Permission)

### 2.1 后端接口拦截 (Server-side Enforcement)
在 `server/routes/guides.js` 和 `server/routes/hints.js` 的保存接口（`POST /`）中，引入原作者写保护鉴权逻辑：

- **校验流程**：
  1. 客户端提交保存请求（`POST /api/guides` 或 `POST /api/hints`）；
  2. 若请求体包含现有规则 `id`：
     - 查询数据库中现有记录的 `authorId`；
     - 若该记录存在，校验当前操作者：`existing.authorId === req.user.id || req.user.role === 'admin'`；
     - 若不匹配，立即拦截并返回 `403 Forbidden`；
  3. 若规则不存在或未提供已有 `id`，正常以当前登录用户的身份插入新规则。

- **错误响应定义**：
  - HTTP 状态码：`403 Forbidden`
  - 响应体：`{ "error": "权限不足：您不是该规则的原作者，无法覆写云端原版规则" }`

### 2.2 插件端界面控制 (Client-side UI Constraint)
- 在插件侧边栏的本地规则列表中：
  - 针对带有 `isDownloaded: true` 的规则，发布按钮提示：`"该规则由他人共享，不可直接覆盖原版"`；
  - 若用户点击发布，明确拦截并提示：`"该规则由 [原作者] 共享，不可直接覆盖原版。如需分享，请新建或复制为您的专属规则"`。

## 3. 本地修改与冲突检测模型 (Conflict Detection Model)

### 3.1 基线指纹机制 (Baseline Signature)
为了精确判断本地规则是否被修改，在本地存储结构中引入**基线指纹 (`baseSignature`)**：

| 规则类型 | 指纹计算公式 (`baseSignature`) | 说明 |
| :--- | :--- | :--- |
| **Guide (引导流程)** | `tour:{name}:{step.url}@{step.selector}@{step.text}` 语义序列串 | 步骤或名称发生变动即判定已修改 |
| **Hint (悬停提示)** | `hint:{url}:{selector}:{text}` 语义序列串 | 文案、选择器或目标 URL 变动即判定已修改 |

#### 指纹生命周期：
1. **下载写入时**：从云端下载成功后，插件计算当前云端快照的指纹，写入本地对象的 `item.baseSignature`，并置 `isDownloaded = true`，`isLocallyModified = false`。
2. **本地保存时**：用户编辑并点击「保存」时，插件重新计算当前内容的语义指纹 `currentSignature`。若 `currentSignature !== item.baseSignature`，自动打上标记 `item.isLocallyModified = true`。
3. **刷新覆盖时**：若用户在冲突时选择了「覆盖本地」，将云端最新快照写入并重新计算更新 `item.baseSignature`，同时复位 `item.isLocallyModified = false`。

## 4. 云端刷新同步与冲突仲裁流程 (Sync Refresh & Conflict Resolution)

### 4.1 刷新时的三态判定

当用户点击本地规则库顶部的 `[🔄 刷新]` 按钮时，对每一条携带 `cloudId` 的规则进行三态评估：

1. **状态 A：无修改静默更新 (Clean Sync)**
   - 条件：本地未被修改（`!item.isLocallyModified`），云端快照有更新。
   - 动作：静默升级本地存储，刷新列表，不需要用户干预。
2. **状态 B：已是最新状态 (Up-to-date)**
   - 条件：本地与云端内容完全一致。
   - 动作：无感保持现状。
3. **状态 C：冲突态 (Conflict Detected)**
   - 条件：`item.isLocallyModified === true` 且 云端数据与当前本地内容不一致。
   - 动作：**阻断自动静默覆盖**，将词条高亮标注，并唤起冲突仲裁界面。

### 4.2 界面视觉标注 (UI Highlighting)
在本地规则列表项上提供即时视觉提示：
- **冲突标签**：在规则标题旁展示醒目的橙色徽章：`⚠️ 本地已修改 (云端有更新)`。
- **状态说明**：悬停时浮出说明：`"您在本地修改了此规则，云端原作者也发布了新版本。"`

### 4.3 冲突仲裁弹窗交互 (Arbitration Dialog)

若刷新扫描发现存在冲突项，弹窗展示给用户确认：

```text
┌─────────────────────────────────────────────────────────────┐
│  ⚠️ 规则同步冲突确认                                        │
├─────────────────────────────────────────────────────────────┤
│  检测到以下规则在本地有定制修改，且云端原作者已更新：       │
│                                                             │
│  📌 谷歌搜索入门                                            │
│     - 原作者: alice                                         │
│     - 本地状态: 已在本地修改步骤/文案                       │
│     - 云端版本: 原作者更新了最新版本                        │
│                                                             │
│  请选择处理方式：                                           │
│                                                             │
│  [🔄 覆盖本地]                  [🛡️ 保留本地修改]          │
│  (放弃本地修改，同步云端最新)    (维持当前本地修改，不覆写) │
└─────────────────────────────────────────────────────────────┘
```

#### 用户决策执行逻辑：
1. **用户点击【🔄 覆盖本地】**：
   - 确认放弃本地修改；
   - 本地规则内容全面覆写为云端原作者的最新快照；
   - 更新 `baseSignature` 为云端新指纹，清除 `isLocallyModified` 标记；
   - 弹出 Toast：`"已成功将规则恢复覆盖为云端最新版"`。
2. **用户点击【🛡️ 保留本地】**：
   - 坚决保持当前本地修改不受任何覆盖；
   - 仅同步最新下载量等统计元数据，**保留本地步骤、文案与选择器**；
   - 本地标记继续保留 `isLocallyModified = true`，解除本次弹窗，列表恢复正常。
