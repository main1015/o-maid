# 产品需求与架构设计说明书

> **产品全称**：O-Maid 云端共享版本 (Multiplayer)  
> **文档性质**：顶层产品需求规格 (PRD) 与系统架构设计纲要

---

## 1. 产品背景与业务愿景

### 1.1 现状与核心痛点
O-Maid 最初设计为一个运行在浏览器本地的单机扩展，帮助用户对常用网页建立操作指引与悬停说明。但单机模式存在显著瓶颈：
- **数据孤岛**：个人编排的优质引导流程无法便捷沉淀与分享给团队同事或外部用户。
- **重复建设**：多人访问相同业务系统或复杂开源工具时，每个人都需要重复录入一遍操作指南。

### 1.2 升级目标：Multiplayer 云端共享生态
- **一键分享**：允许创作者将本地打磨好的引导任务与提示一键上传至云端共享。
- **场景化自动发现**：任何用户访问特定域名（例如 `github.com`、内网 OA 等）时，插件能自动探查并推送匹配的云端指引，实现“开箱即用”。
- **闭环管理**：为管理员与创作者提供一体化的 Web 监控台，支持数据审核、修改密码与用户注销。

## 2. 系统总体架构设计

系统采用典型的前后端分离 + Chrome 扩展注入架构：

```
+-------------------------------------------------------------+
|                     浏览器环境 (Client)                      |
|                                                             |
|  +---------------------------+   +-----------------------+  |
|  |   宿主网页 (任意业务网站)   |   | Web 控制台 (Dashboard) |  |
|  |                           |   | (http://localhost:port)| |
|  | +-----------------------+ |   +-----------+-----------+  |
|  | | O-Maid 注入 ShadowDOM | |               |              |
|  | | (ui-manager.js)       | |               |              |
|  | +-----------+-----------+ |               |              |
|  +-------------|-------------+               |              |
|                |                             |              |
|    chrome.storage.local (全局跨域存储)         |              |
|                |                             |              |
+----------------|-----------------------------|--------------+
                 | (RESTful JSON 请求)          |
                 v                             v
+-------------------------------------------------------------+
|                      Node.js / Express 服务端                |
|                                                             |
|   ├── server.js (入口与静态托管)                              |
|   ├── routes/ (auth.js, guides.js, hints.js, stats.js)      |
|   ├── middleware/ (auth.js JWT鉴权)                         |
|   └── database.js (SQLite3 本地轻量持久化)                   |
+-------------------------------------------------------------+
```

## 3. 核心业务流程与时序

### 3.1 规则发布流程
1. 用户在任意网页打开插件「本地库」，点击某个任务卡片右侧的 **`☁️ 发布`** 按钮。
2. 插件校验当前是否已登录：
   - 若未登录：友好弹窗提示，并自动跳转至「云端账号」登录/注册视图。
   - 若已登录：提取当前网页域名、任务名称及步骤 JSON，向后端发起 `POST /api/guides`。
3. 后端校验数据完整性，入库保存并返回成功响应。
4. 插件弹出绿色成功通知，并在 Web 控制台大屏实时显现该条发布动态。

### 3.2 云端发现与下载流程
1. 用户打开特定网页（例如 `www.google.com`），展开插件切换至「云端发现」Tab。
2. 插件静默读取当前页面域名（`www.google.com`），调用 `GET /api/guides?domain=www.google.com`。
3. 列表呈现当前域名的共享指引，用户点击 **`⬇️ 下载`**。
4. 插件将任务复制写入本地 `chrome.storage.local`，并通知后端调用 `POST /api/guides/:id/download` 计数累加。
5. 用户即可在「本地库」中随时离线运行该任务。

## 4. 非功能性需求 (NFR)

1. **性能与轻量化**：
   - 坚持“按需触发”原则：云端发现只在用户主动点击 Tab 或刷新按钮时拉取，绝不在每个网页加载时盲目发起网络请求。
2. **零侵入与沙箱隔离**：
   - 插件界面完全封闭在 Shadow DOM 内，不向宿主网页注入全局变量，不篡改宿主 DOM 原有结构，CSS 互不污染。
3. **数据一致性与全局漫游**：
   - 登录态与 API 配置必须具备全局跨标签页同步能力，严禁使用按域名物理隔离的原生 `localStorage`。
4. **易部署性**：
   - 后端免除庞大外部中间件依赖，采用单机 SQLite 存储，单脚本 `./start-server.sh [端口]` 即可完成启动与服务挂载。

## 5. 后续规划 (Phase 2 & 3)

1. **规则点赞与评级系统**：支持用户在云端对高质量引导进行点赞与打星评分。
2. **私有/团队空间分享**：支持生成 6 位提取码（Share Code），实现团队内部定向共享而非全网公开。
3. **可视化步骤实时预览**：在下载前，支持以弹出卡片形式预览完整步骤序列。
